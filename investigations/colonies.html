📋 Executive summary in-progress

Question. How many whole-cell E. coli agents can we fit per HPC node, and at what per-cell wall-time cost, so that a colonies-on-HPC workload is realistic to plan against? More fundamentally: does the multi-cell colony composite (each cell embedding the full 55-process WCM via EcoliWCM) actually support clean parallel growth + division at scale, or are there per-cell-cost or per-cell-RAM cliffs that show up only at N > 1?

Hypothesis. After fixing daughter-process hydration, the colony composite scales linearly with N (per-cell wall ≈ constant, per-cell RAM ≈ constant) on a single machine for N up to at least 8, and the dominant cost is the inner EcoliWCM (not pymunk or scheduler). HPC sizing is then a function of (RAM_per_node / RAM_per_cell, cores_per_node / cells_per_process_at_realtime). The single bottleneck visible at laptop scale will be the Python GIL — process-bigraph composites are single-threaded by design, so HPC scaling means scaling processes, not cells per process.

Overview

This study asks whether is the pure whole-cell colony composite ready to scale on HPC?. We recorded 3 findings confirm the expected biology, 3 novel computational results. Gate decision: Passed. Gate cleared. Next: colonies-02-hpc-deployment

Purpose & background (study design)
Question. Is the pure whole-cell colony composite ready to scale on HPC? Specifically: can N parallel EcoliWCMs grow and divide cleanly for ≥2 generations inside one composite, and how does wall-time / RAM / per-tick cost scale with N on a single machine — well enough that we can confidently project a cells-per-HPC-node budget?
Mechanism / Model change. The `colony` composite generator (v2ecoli/composites/colony.py) wires N copies of EcoliWCM (v2ecoli/bridge.py) into a pymunk 2D physics environment. Each EcoliWCM holds an internal Composite of the 55-process baseline. At cell division the bridge returns a structural update (_remove mother, _add two daughter EcoliWCMs) that the outer composite engine must hydrate. We sweep N ∈ {1,2,4,8} and instrument per-tick costs.
Expected outcome. After the Build phase fix, a pure-WC N=2 colony runs past first division to 4 ticking cells without the manual-hydration workaround in reports/colony_report.py. In the N-sweep, per-cell wall time stays within ~2× of the N=1 cost (i.e. no super-linear blow-up from coupling/contention), peak RSS scales close to linear, and we can name the dominant bottleneck (likely GIL, pymunk serial step, or RAM-per-cell).

◆F-02-gil-bottlenecknew result
The GIL is the dominant bottleneck at colony scale. Process-bigraph composites are single-threaded by design — one process uses ~1 CPU core regardless of how many cells it holds. Scaling means more processes, not more cells/process.
What we saw: pymunk_step_ms ≈ 0.1 ms/tick (free); ecoli_ms grows linearly with N ms/tick
Why: All 55 inner WCM steps are walked sequentially in one Python thread. pymunk is free even at N=8, so any super-linear cost would have to be in the EcoliWCM update — but per-cell stays flat. The only ceiling visible is total wall vs realtime per process, which crosses ~1.0 around N≈13.
→ Next: Seed gil-aware-engine-research follow-up.

Methodological findings (1)

◆F-05-build-phase-bugsnew result
Three independent bugs blocked daughter hydration through the engine and had to be fixed before the Decide phase could run.
What we saw: After all three fixes, pure-WC N=2 force-divided to 4 hydrated daughters that all advance on the next tick.
Why: (1) viva-munk apply_updates_with_realize unpacked 2 values from bigraph_schema.core.realize, which now returns 3 (escape_merges) — every structural _add crashed. (2) v2ecoli/colony.py wired only mass/volume/exchange outputs on initial cells; _handle_division writes to `agents` with no wire, so mother updates had nowhere to land. (3) v2ecoli/bridge.py _handle_division hard-coded `interval=60.0` for daughters; `interval` is not in config_schema, so daughters ticked once per 60s instead of inheriting the mother's 1s cadence.
Technical detailstest: daughters-hydrated
run: build-smoke-n2

Key assumptions

  • Pure-WC colony at N=2 is feasible to run past 2 generations within ~90 min sim time on a developer laptop (40-min doubling × 2 + slack).
  • The dominant per-tick cost is the inner EcoliWCM update, not pymunk integration (validated by per-tick split in the harness).
  • Peak RSS measured with psutil after each run captures the steady-state RAM cost per cell accurately enough for HPC extrapolation (±20%).
  • Single-machine N-sweep extrapolates monotonically to per-node HPC sizing — i.e. no surprise breakdowns from network or filesystem at HPC scale that aren't visible here. (This is the assumption colonies-02 will test directly.)

Limitations

  • Single-machine only; cross-node HPC scaling is colonies-02's job.
  • 90 min sim window is one full doubling + a buffer for the second division, not an N-generation run.
  • Per-cell EcoliWCM internal cache is shared (cache_dir is the same path). RAM extrapolation may UNDERESTIMATE HPC RAM if HPC runs use per-cell caches.
  • pymunk is single-threaded; GIL contention may dominate before any HPC-relevant bottleneck shows up. The Decide report must call this out explicitly.
